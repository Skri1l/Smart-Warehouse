# 0009. Devices push images over HTTP with an ordered on-device outbox

Status: Proposed
Date: 2026-10-07 (revised 2026-10-08 against the backend's published Swagger spec)

## Context

[RFC-0001](../rfcs/0001-image-ingestion-and-recognition-pipeline.md) proposes the upload as `POST /api/v1/device-events/images` (multipart: `shelfId`, `deviceId`, `capturedAt`, image), answered with `202 Accepted`. It leaves open how a device behaves when the backend is unreachable, and how it authenticates.

The backend that actually exists (its OpenAPI spec at `/v3/api-docs`, Swagger UI at `/swagger-ui.html`) offers something different today:

- `POST /image-events` with JSON `{deviceId, imagePath, capturedAt}` → `201` + the new id. There is **no endpoint that accepts the image bytes**.
- `capturedAt` is a Java `LocalDateTime` (no zone). The backend stamps `receivedAt` with its own local clock.
- Device ids are generated by the database. `POST /devices {deviceKey, shelfId}` → `201` + id, and `GET /devices` lists `{id, deviceKey, status, lastSeenAt, shelfId}`. There is no lookup by key.
- `PATCH /devices/{id}/heartbeat` → `204`.
- No authentication on any endpoint yet. Everything is open for development.

Further facts:

- NFR-02: a failure must not corrupt stock, and failed events must be retryable.
- The backend derives a stock **delta** from consecutive images of the same shelf. If frames of one shelf arrive out of order, the deltas are wrong, and the error is silent.
- Shelf Wi-Fi in a warehouse is unreliable, and a Pi can lose power.
- A retried request may already have been stored by the backend: the response was lost, not the request.

## Decision

We will use plain HTTP push from device to backend, **speaking the API the backend publishes**, with these device-side rules:

1. **Protocol follows Swagger.** By default (`protocol = "image-events"`) each frame is stored on the device and reported with `POST /image-events`, with `imagePath` set to the stored file. The RFC-0001 multipart upload stays implemented behind `protocol = "multipart"`, for the day the backend accepts image bytes. Switching is a config change only.
2. **Identity is resolved by key.** The device is configured with `deviceKey` and `shelfId`. On start it finds its id with `GET /devices` and checks that the backend links it to the same shelf. The emulator registers missing devices with `POST /devices`. Real devices don't by default: an administrator registers them. A configured `device_id` is optional. It lets a device start while the backend is unreachable.
3. **Persistent outbox, strict order.** A frame that cannot be delivered (no connection, timeout, `5xx`, `408`, `429`) is written to an on-disk FIFO. While the outbox is non-empty, new frames of that shelf queue behind it, never ahead. The outbox is flushed before each new capture and after every successful heartbeat.
4. **Final errors are kept, not retried.** Any other `4xx` means the request itself is wrong (unknown device, bad data). The frame moves to `outbox/rejected/` and is logged as an error.
5. **Timestamps are set at capture time** and preserved through retries. For `image-events`, `capturedAt` is sent as a zone-less local datetime (`timestamp_zone = "local"`, or `"utc"`), matching the backend's `LocalDateTime`. For `multipart` it is UTC with `Z`.
6. **Liveness via the existing heartbeat endpoint**, every 30 s by default.
7. **Proposed for the future upload endpoint** (`multipart` only): `X-Device-Key: <deviceKey>` header for device authentication, and a `clientEventId` UUID, unchanged across retries, for deduplication. The `image-events` JSON carries exactly the three documented fields.

## Alternatives considered

- **Implement only RFC-0001 and wait for the backend**: rejected. The emulator and the demo would be blocked on a backend endpoint that has no date, while a working API exists.
- **Implement only the current JSON API**: rejected. The image bytes never reach the server that way, which a deployed (non-laptop) setup will need. Keeping the multipart path behind a flag costs one method.
- **Fixed `device_id` in config**: rejected as the primary identity. Ids are database-generated and differ between environments (local, Docker, cloud). The key is stable.
- **MQTT broker (Mosquitto) between devices and backend**: rejected for the MVP. It adds a broker to deploy and secure (Milestone 8) and a second protocol for the backend, and 0.5–5 MB images are an awkward fit for MQTT payloads.
- **Fire-and-forget HTTP (no outbox)**: rejected. Any Wi-Fi drop loses a shelf event and breaks NFR-02.
- **In-memory retry queue only**: rejected. A power cycle loses everything queued.
- **Send the newest frame first, backfill later**: rejected. It corrupts stock deltas, which depend on frame order.
- **Device auth with a user JWT or mTLS**: rejected for now. A user token doesn't model a device, and mTLS needs certificate provisioning per Pi. A per-device key over HTTPS is enough for the diploma.

## Consequences

- The emulator works against the real backend today. Devices, image events and heartbeats appear in Swagger and in the database.
- **With `image-events`, the image stays on the sending machine.** Recognition can only open it where `imagePath` exists, which is fine when backend, ML service and emulator share a machine (the demo laptop) and not for a Pi on the network. The backend needs an upload endpoint (RFC-0001) before real shelves can be recognised remotely. The device side for that is already done.
- No frame is lost to a network or backend outage. Each shelf's frames reach the backend in capture order, possibly late. The backend must order by `capturedAt`, not by arrival time.
- `image-events` delivery is at-least-once **without** a deduplication key: a retry after a lost response can create a duplicate `ImageEvent`. The multipart path fixes this with `clientEventId` once the backend supports it.
- Zone-less `capturedAt` is only unambiguous while device and backend agree on the zone. That holds for one warehouse. Revisit (switch the backend to `Instant`/`OffsetDateTime`) if devices in other zones appear.
- Without authentication any client can post events for any `deviceId`. That is accepted while the whole API is open for development, and must be closed together with real auth.
- The Pi keeps every still in `capture_dir`. There is no retention policy yet, so add one before long-running deployments.
- All of this lives in `Device/shelf_agent/transport/`, `registration.py` and `agent.py`, shared by the device and the emulator ([ADR-0008](0008-shelf-agent-shared-core.md)).
